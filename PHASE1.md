# Phase 1 — what changed, how to run it, how to read the results

## What Phase 1 adds (see `CHANGES.md` for the full list)
Idle back-off, fast-attack / slow-release controller, overload guard, looser timeouts, message and byte counters,
fault injection (loss, link cut, indirect probing on/off), four modes (adaptive + three fixed baselines),
and the `eval_v2.py` harness. **Cluster size is now a parameter (`--nodes N`, 5 to 26).**

## How to run
See `RUNBOOK.md` (step by step) and `README.md` (all flags).

## How to read the results
- `results/summary.md` is generated by `python3 eval_v2.py analyze`. Rows are grouped by cluster size.
- Convergence: seconds from the crash until *every* survivor has logged the victim DEAD (only log lines after the crash count).
- Bandwidth: messages per second and bytes per second sent by nodes A, B and D, which are never killed.
  Counted at the sender before fault injection, so it measures what the protocol tried to send.
- Loss / partition: nobody crashes, so every SUSPECT or DEAD verdict is a **false** verdict. Lower is better.
- p-values: Welch t-test against `fixed-base`. p > 0.05 means *no demonstrated difference*.

## What the smoke runs showed (n = 1-2 per cell, NOT statistically meaningful)

5 nodes (`results/smoke_5nodes.jsonl`):
- Calm traffic: adaptive about 46% below the 1.5 s baseline and about 80% below the 0.5 s one.
- Crash detection: adaptive about as fast as the 0.5 s baseline, faster than the 3 s one.
- During churn adaptive sends about twice the baseline's traffic.

20 nodes (`results/smoke_20nodes.jsonl`, one trial each, one-core sandbox):
- Calm traffic: 0.60 msgs/s per node adaptive vs 1.49 for the 1.5 s baseline (-60%).
- Single-crash convergence: 9.4 s adaptive vs 12.6 s fixed-base.
- Link cut A<->B: no false verdicts with indirect probing, 19 false DEAD without it.
- 30% loss: 404 and 479 false DEAD in 45 s (two runs). That is about 1.2 per ordered node pair, the same per-pair rate as the 5-node smoke (about 1.15), so the loss behaviour does not get worse per pair with size, but it is not good.

## Finding: the overload guard cannot engage at realistic probe rates
The guard fires when at least max(3, 75% of live peers) *distinct* targets fail within 6 s. A node probes one target per
interval (0.3 to 3 s), so in 6 s it sees roughly 2 to 4 probes. Three distinct failures therefore means nearly every probe failed.
At 20 nodes the 75% rule asks for 15 distinct failures, which is impossible. The smoke runs agree: guard engagements were 0 at 20 nodes
and rare at 5. **So "the guard has no measurable effect" is currently a statement about the guard's trigger, not about the idea.**
Replacing it is the first item of `PHASE2_PLAN.md`.

## Limits (say these first in any write-up)
- Everything is localhost; faults are injected inside the process, not real network faults.
- The Windows cascade is still not reproduced or fixed.
- 20 processes on one machine share CPU; check CPU during runs.
